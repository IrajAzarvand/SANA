# SANA AI

این پوشه واحد مستقل قابلیت‌های هوش مصنوعی در مخزن SANA است. قابلیت‌ها در زیرپوشه‌های جداگانه نگهداری می‌شوند تا توسعه، آزمون، مستندسازی و تغییر هرکدام بدون درهم‌آمیختن مسئولیت‌ها انجام شود.

## ساختار فعلی

```text
AI/
├── README.md
└── auto_decoder_generator/
    └── README.md
```

## قابلیت‌های برنامه‌ریزی‌شده

- `auto_decoder_generator/`: تحلیل پروتکل‌های ناشناخته، بررسی منابع، تولید و آزمون دیکودر و آماده‌سازی انتشار کنترل‌شده.
- `vehicle_behavior_analysis/` (آینده): تحلیل رفتار خودرو؛ این پوشه فقط هنگام شروع طراحی و پیاده‌سازی آن قابلیت ایجاد می‌شود.
- `intelligent_reporting/` (آینده): گزارش‌گیری هوشمند؛ این پوشه نیز پس از تعریف نیازمندی‌ها ایجاد می‌شود.
- قابلیت‌های جدید باید هرکدام پوشه، README، قرارداد ورودی/خروجی و تست‌های مستقل داشته باشند. نام‌های آینده نمونه‌اند و به معنی وجود یا پیاده‌سازی فعلی این قابلیت‌ها نیستند.

## اصول معماری

1. هر قابلیت باید مسئولیت و مستندات مستقل داشته باشد.
2. کد AI نباید مستقیماً به جزئیات داخلی سرویس‌های دیگر وابسته شود؛ ارتباط باید از طریق قراردادهای روشن و نسخه‌پذیر باشد.
3. خروجی تولیدشده توسط AI قابل اعتماد فرض نمی‌شود؛ باید آزمون، اعتبارسنجی و کنترل امنیتی شود.
4. اجرای کد تولیدشده در محیط اصلی ممنوع است؛ اجرای آزمایشی باید ایزوله و محدود باشد.
5. وضعیت‌ها، خطاها، نسخه‌ها و منشأ خروجی‌ها باید قابل ردیابی باشند.
6. تا زمانی که یک قابلیت واقعاً پیاده‌سازی نشده، README آن باید این موضوع را صریحاً اعلام کند.

## مرز با سرویس GPS

واحد AI در ریشه مخزن قرار دارد؛ سرویس اجرایی دریافت GPS در `sana-gps/` است. برای تولید دیکودر، کد تحلیل/تولید در `AI/auto_decoder_generator/` نگهداری می‌شود، در حالی که دیکودر تأییدشده و قابل استفاده در Runtime باید در `sana-gps/app/protocols/decoders/` منتشر شود. انتشار باید کنترل‌شده، نسخه‌پذیر و قابل بازگشت باشد. واحد AI نباید Listener شبکه یا سرویس GPS موازی بسازد؛ نمونه‌های بسته را از مسیر موجود دریافت می‌کند و فقط از طریق قرارداد مشخص با Runtime یکپارچه می‌شود.

سند تصمیمات GPS و تولید دیکودر: [telemetry.md](../telemetry.md).
